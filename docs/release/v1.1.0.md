# repl-lang v1.1.0 — Any Parser, Any Entry

**One new method and two fixes.** `Input::is_incomplete_relative` gives
parsers that report positions from the start of the entry's text, such as a
lang-forge language, a correct continuation check in every entry, not just
the first. Saved multi-line history entries now come back with their lines
intact. `Input::is_incomplete` is unchanged.

## What is repl-lang?

The state of a read-eval-print loop, with the language and the terminal left
out. A `Session` runs a language's pipeline on each entry as it is typed, uses
the pipeline's own parse errors to tell "unfinished" from "wrong", and commits
every finished entry to one source map so diagnostics can point anywhere in the
session. An `Editor` handles the line being typed (motion by visible character
and by word, kill and yank, history), driven by `Edit` commands the host maps
from its own key events. It is one of the FEAT-tier crates of the `-lang`
language-construction family.

## What's new in 1.1.0

### `Input::is_incomplete_relative` (ISSUES M72)

`Input::is_incomplete` says "ask for another line" when every parse error sits
at the end of the input, and it reads error spans as **global** positions in
the session's source map. That is what a pipeline gets when it lexes with
`Input::cursor`. A parser that runs on `Input::text` alone reports positions
from `0` instead. In the first entry the two coincide; from the second entry
on, its end-of-input errors fall before the entry's global end, and
`is_incomplete` judged every unfinished entry complete:

```text
> let a = 1;
> let b = (2 +
error: expected expr, found the end of the input      <- with is_incomplete
...                                                    <- with is_incomplete_relative
```

`is_incomplete_relative` applies the same rule counted from the start of the
text. Pick the method that matches how the pipeline reads its input:

| The parser… | Its spans are | Use |
|---|---|---|
| lexes with `Input::cursor`, or adds `Input::base` itself | global | `is_incomplete` |
| parses `Input::text` as a standalone string (lang-forge) | relative to the text | `is_incomplete_relative` |

```rust
use diag_lang::{Diagnostic, Label, Severity};
use repl_lang::{Session, Span, Status};

let at = |pos: u32| Diagnostic::new(Severity::Error, "expected", Label::new(Span::empty(pos), ""));

let mut session = Session::new();
session.feed("let a = 1;", |_| Status::Complete(()))?; // occupies 0..11
session.feed("(2 *", |input| {
    assert!(input.is_incomplete_relative(&[at(4)]));  // the end of "(2 *"
    assert!(!input.is_incomplete_relative(&[at(1)])); // mid-text: wrong
    assert!(input.is_incomplete(&[at(11 + 4)]));      // the same place, global
    Status::Complete(())
})?;
# Ok::<(), repl_lang::SessionError>(())
```

**Why a method and not a guess.** A span that starts at or after the entry's
base and ends within its text fits both coordinate spaces, so any automatic
choice misjudges some errors from one kind of parser. That includes the
documented global path. Saying which space the spans are in removes the
question. A second method was chosen over a `Coordinates` parameter: there are
exactly two spaces, each tied to how the pipeline reads its input (`cursor` or
`text`), so a pair of methods mirrors that pair, adds no new type, and reads
plainly at the call site.

### History keeps multi-line entries whole (ISSUES M73, patch part)

`Editor::add_history` removed every control character, newlines included, so
an entry saved as `"let x =\n  42"` came back as `"let x =  42"`, and `"a\nb"`
as `"ab"`: one token where there were two. It now keeps newlines and tabs,
turns `"\r\n"` and a lone `'\r'` into `'\n'`, and still removes every other
control character, `ESC` included, so a saved escape sequence cannot reach the
terminal through the line.

```rust
use repl_lang::{Edit, Editor};

let mut editor = Editor::new();
editor.add_history("\u{1b}[1mbold");
editor.add_history("let x =\r\n\t42");
assert!(editor.history().eq(["[1mbold", "let x =\n\t42"]));
assert!(editor.apply(Edit::HistoryPrev));
assert_eq!(editor.line(), "let x =\n\t42");
assert_eq!(editor.column(), 3); // on the second line: a tab (one column) and `42`
```

Because a recalled entry can now put them in the line, the editor handles
them: a newline is a display unit of its own (the cursor stops on both sides of
it, one backspace removes it), a tab is a unit one column wide, and `column`
counts from the start of the cursor's own line. Typing and pasting still
refuse every control character. A line without a newline or tab, which is
every line 1.0.0 could hold, behaves exactly as before.

### Smaller changes

- `#![deny(warnings)]` is no longer set in the library (ISSUES F03), so a lint
  added by a newer toolchain cannot break a downstream build. CI still builds
  with `-D warnings`.

### Planned for later

The rest of M73 is recorded in `dev/ROADMAP.md`: an explicit "unterminated"
signal from the parser, which would make completeness independent of where
errors are placed, and an incremental feed, since re-running the pipeline on
the whole entry after every line costs O(lines²) for a long entry.

## Breaking changes

**None.** `is_incomplete_relative` is new; every existing method keeps its
signature, and `is_incomplete` keeps its exact 1.0 behaviour. History entries
now keep newlines and tabs, the fix above; `docs/API.md#stability` records it,
along with what 1.0.0 did.

## Verification

Run on Windows x86_64, Rust stable and the 1.85 MSRV:

```bash
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo clippy --all-targets --all-features -- -D warnings
cargo clippy --all-targets --no-default-features -- -D warnings
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --all-features
cargo +1.85 clippy --all-targets --all-features -- -D warnings
cargo test --all-features
cargo test --no-default-features
cargo +1.85 test --all-features
cargo bench --no-run
```

All green. New tests:

- `tests/lang_forge.rs` drives a statement language forged with lang-forge
  1.0.1 (a dev-dependency from crates.io) through sessions of several entries
  using `is_incomplete_relative`, some entries shorter and some longer than
  their base. It checks continuation and mid-entry errors. It checks that the
  verdict equals `is_incomplete`'s on the same spans shifted by the base, and
  that `is_incomplete` misjudges the unshifted spans.
- New properties: the relative method matches the definition in any entry,
  and the two methods agree under a shift by the base. The 1.0
  `is_incomplete` property is unchanged.
- The editor model covers recalled entries with newlines, tabs, and carriage
  returns, with a property that starts every case from one.
